\section{Experimental Results and System Integration}

\subsection{Evaluation Protocol and Experimental Results}
Speaker verification is evaluated with 10,000 deterministic balanced trials on held-out VIVOS speakers: 5,000 genuine trials and 5,000 impostor trials. Given two embedding vectors $a$ and $b$, the runtime score is cosine similarity:
\[
    \mathrm{score}(a,b) = \frac{a \cdot b}{\lVert a \rVert_2\lVert b \rVert_2}.
\]
The report uses equal error rate (EER), the point where false reject and false accept rates are equal, and minimum detection cost function (minDCF). SID Top-1 accuracy is computed by averaging five enrollment embeddings for each test speaker, then assigning each remaining query recording to the highest-scoring profile.

\subsection{Speaker Enrollment, Verification, and Identification Integration}
\subsubsection{Enrollment procedure and stored voice data}
Enrollment starts after the new user has created a Dearly account. In \emph{Settings -- Voice enrollment}, the user records five displayed Vietnamese prompts with visible $0/5$--$5/5$ progress. A caregiver may help an elder operate the device, but the enrolled speaker must say each prompt personally. Android's amplitude-based VAD requires at least 0.8 seconds of sustained activity; silent or too-short recordings are deleted locally and the elder is asked to record that same phrase again. The Android client sends only an accepted temporary audio file and its \texttt{phrase\_index} 0--4 to the authenticated \texttt{/api/v1/voice/enroll} endpoint. The API obtains the account identifier from the JWT rather than trusting a client-provided user identifier.

The Go API forwards the recording to FastAPI. The AI service validates the audio, performs a second intelligible-speech check with ASR before extracting an ECAPA-TDNN embedding, and deletes the temporary server-side file in a \texttt{finally} block. Thus, a direct API client cannot enroll a silent/unintelligible recording merely by bypassing Android's VAD. The Android client also deletes its temporary recording after the upload. Consequently, the enrollment database contains embeddings, not raw voice recordings. Each of the five phrase vectors is stored first; after phrase 5, the backend computes an element-wise mean and stores the resulting runtime profile at \texttt{phrase\_index=-1}. Re-recording a phrase upserts that phrase's row and recomputes the average when all five inputs are available. A reset deletes all enrollment rows for that user.

\subsubsection{Verification and identification at runtime}
For SV, ECAPA extracts an embedding from fresh speech and the AI service computes cosine similarity against the signed-in user's average profile. The deployment threshold is currently 0.80. A pass produces a random grant bound to the user and protected intent; its SHA-256 hash is stored, it expires after two minutes, and the medication endpoint consumes it exactly once. The API records protected verification attempts, rejects a replay of a previously successful raw recording for 24 hours, and pauses verification for 15 minutes after five failed attempts. The named-dose/time read-back followed by a new spoken confirmation is an interaction check; exact raw-audio replay is blocked, but a dedicated anti-spoof/liveness model is not yet part of the system and re-encoded playback remains a stated limitation. For SID, the backend supplies only average profiles for the caller and directly linked caregiver/elder accounts. FastAPI returns the highest-scoring identity only when it meets the SID threshold. The Go API then independently re-checks that the returned identity is still in that trusted relationship group before it loads a name or medication schedule.

Figure~\ref{fig:protected-flow} describes the hands-free protected medication flow. The elder does not need to tap a particular dose: they can say, for example, ``Tôi đã uống Amlodipine rồi.'' Dearly extracts the medicine name and finds today's matching unpaid dose, but does not update it yet. Dearly reads back the medicine and scheduled time, for example, ``Bác xác nhận đã uống Amlodipine lúc 08:30 phải không?'', then asks the elder to say ``Đúng rồi.'' SV runs on this fresh confirmation recording before the grant is issued. A silent, too-short, replayed, or failed confirmation leaves the dose unchanged and asks the elder to retry.

\subsection{Implementation Validation and Demonstration Evidence}
\paragraph{SID personalization beyond the name.} After a SID match is accepted and its caregiver/elder relationship is re-checked, the backend loads preferences only for that identified person: gentle or direct reminder wording, Vietnamese TTS speed, an optional preferred contact, and daily-schedule inclusion. The response contains these preferences; Android applies the selected rate to that TTS response and displays a small personalization label. Public requests and untrusted identities cannot read them.

The completed engineering checks include AI-service linting and focused tests, Docker Compose configuration validation, backend unit tests for voice grants, replay hashing, and general responses, protected-route authorization checks, and successful Android debug build and unit-test runs. The public voice route is reachable without a token, whereas the medication update route rejects unauthenticated requests or requests without a valid voice grant. These checks validate the contract and the compiled client; they do not replace a recorded demonstration with real enrolled voices.

\subsection{Limitations and Conclusion}
Dearly provides a reportable end-to-end design: VIVOS fine-tuning improves held-out verification performance, ECAPA embeddings drive both SV and SID, and a server-side grant prevents ASR, intent classification, or SID alone from authorizing a protected medication update. The public assistant demonstrates a genuinely non-authenticated function without exposing private information.
